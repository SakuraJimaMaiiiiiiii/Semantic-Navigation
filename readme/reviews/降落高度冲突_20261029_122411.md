# 降落高度冲突核查

实验：run_20261029_122411_798096。
证据：exploration/private/landing_failure.json（读取landing对象）。

## 已证实

- 起飞前UE位置为[0,0,0]，地面碰撞为BP_Road_2。
- 近地准备使用XY位置保持+Z下降速度，速度上限0.12m/s。
  PX4 NED z从-1.494下降到-1.158，仅下降0.336m，准备阶段超时。
- 发送LAND时UE z=-1.152；最终UE z仍为-1.152，未继续下降。
- 最终PX4 z=-1.191，相对保存地面高1.170m，速度0.0067m/s。
- PX4 ALTITUDE.bottom_clearance却为0.100m，且landed_state=1、armed=false。
- AUTO.LAND已接管，Offboard发送线程已经停止。
- 最终HOME_POSITION改为z=-1.228、海拔51.195m，而发送LAND前仍接近起飞地面
  z=-0.026、海拔49.992m。因此最终relative_alt=-0.037m不能证明回到了起飞地面。

这不是只有PX4局部高度漂移的确认误报：UE也显示飞机仍高于起飞地面约1.15m。
没有证据支持删除落地高度检查或将停桨直接算作落地。

## 尚未证明

当前记录没有PX4 ULog中的distance_sensor、vehicle_local_position.dist_bottom、
vehicle_land_detected及推力时间序列，因此不能确定最初错误发生在
CopterSim地形/接触模型、距地高度输入还是PX4估计器。
ALTITUDE.bottom_clearance与UE位置矛盾是排查入口，并非已证明某一个传感器损坏。

本地Firmware源码mc_pos_control/MulticopterPositionControl.cpp显示，
flying_but_ground_contact时会清除位置/速度参考并重置积分；这说明
仅靠加大发送下降指令或延长Python超时不一定有用，但不代表本次已证明触发该分支。

## 下一项验证

在相同场景做短距离起降，采集PX4 ULog，对齐UE高度与
distance_sensor、vehicle_local_position.dist_bottom(_valid)、
vehicle_land_detected的ground_contact/maybe_landed/landed、推力输出及模式变化。
确认哪个信号最先在UE仍高于地面时变成“近地/接触”。
同时核对CopterSim加载的地形和UE车库实际地面是否一致。
不自动重解锁，不改落地门槛，不修改外部飞控参数；本轮仅完成证据核查。
