## 确认的延迟来源

旧 LiDAR 工作线程按“局部融合 → 全局融合 → 再等完整更新周期”串行执行。该次运行的统计记录：局部融合最大 6.203 s，全局融合最大 6.437 s；全局融合占用线程时，局部地图无法接收下一次融合。EGO 地图停更阈值为 0.6 s。

这些运行耗时含当时资源竞争，不能仅凭最大值推断单个算法的纯计算代价。单独离线重放 3000 点的同一时刻扫描，在 Windows 项目环境中局部融合约 0.0116 s、首次快照约 0.00045 s，说明在线竞争/排队不能忽略。该离线数字不是实际飞行延迟保证。

## 实际修改

1. `mapping/lidar_mapping_worker.py`：局部、全局融合分别处理各自最新一帧，保留已有有界的“只取最新帧”语义；全局融合不再占住局部融合的执行循环。更新周期按融合开始时间计算，耗时超过周期后不额外再睡一个完整周期。线程失败继续交回主任务上报。
2. `mapping/local_occupancy_grid.py`：缓存只读的 states / inflated_occupied / observed；几何变化时失效，RGB-D 观测和前向净空字段仍及时更新。避免每个规划读取都重新构造/膨胀同一份占据地图。
3. `navigation/route.py`：从全局自由格补充未观测局部格的检查改为数组批处理，保持原覆盖条件。用 W020 快照对比修改前后，free 和 occupied 集合一致；该快照耗时约 0.02 s，未观察到明显提速，不将其认定为本次主要瓶颈。
4. `planner/ego_local_planner.py`：同一航点的有效旧曲线按当前机体位置取剩余段；当前连接段及所有剩余段在新地图上通过复核后复用。目标变化或新障碍阻断曲线时重新求解。新轨迹时钟从整个规划完成时开始，求解耗时不再被误算成已经执行的轨迹时间；暂停后求解使用实测运动状态。
5. `vehicle/rfly_multirotor.py`：恢复稳定时间从可执行规划完成的时刻计，不混用规划前后的时间。仍要求已有稳定时长与低速条件，未放宽障碍净空或地图超时阈值。
6. `navigation/mission.py`、`planner/native_ego_local_planner.py`：细分记录健康检查、快照、栅格投影、局部规划、原生求解、轨迹净空复核、语义路径复核、规划后复核与曲线复用时间。数据进入现有失败快照/控制状态，不增加终端逐帧打印。

同一受阻首段仍由局部绕障检查决定是否可执行。本轮通过复用已验证曲线减少反复求解和无移动超时，不把地图停更当作真实障碍去永久封闭通道，也不向地图强行添加自由格。
