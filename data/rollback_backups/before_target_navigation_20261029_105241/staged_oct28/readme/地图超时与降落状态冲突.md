# 地图超时与降落状态冲突（2026-10-10）

本轮 `run_20261010_102751_000237` 的首先触发异常是 `semantic_global_map_stale`，不是 VIO 审计工具报错。结束快照中规划为 `route_clear`，局部地图时间戳比全局地图新约 0.7 秒；这只能说明两个地图更新不同步，不能据此确定阻塞发生在哪里。雷达报告还有 1061 次位姿同步拒绝，但旧日志没有逐帧积分耗时，不能断言它是此次全局超时的唯一原因。

## 本次修改

- 探索检测到局部或全局地图过期时，先发送一次悬停，再用已有 `map_timeout`（默认 3 秒）作为恢复等待上限。原来的新鲜度要求不变，不使用过期地图继续移动。
- 两张地图检查恢复后继续探索，并重置运动进展计时；持续超时或任务截止仍然退出。
- `lidar_camera_alignment.json` 新增最近接收、接纳和积分的雷达时间戳，以及局部/全局积分的最近耗时、最大耗时和当前阶段，用于区分输入停顿、位姿同步拒绝和地图积分阻塞。
- 降落继续采用原 `sendMavLand` 方式。若持续收到新鲜且推进的遥测，PX4 和 SDK 都表示未解锁、PX4 表示在地面、速度很低，但高度超过容差，记录 `disarmed_height_conflict`，不再等满降落超时。
- 上述冲突只允许已停桨后的通信清理，不代表落地确认，也不能开启下一次地图导航。仍解锁、遥测过期或未确认状态时，保留禁止强制停桨的行为。

## 重新运行

本轮没有改 C++ 模块，无需重新编译。若 UE 中飞机已经停桨并停在异常位置，先重置仿真到正常起点，再运行 `python run_explore.py`。代码不会在位置和落地状态冲突时自动重新解锁。

重新测试时观察 `MAP_UPDATE_WAIT` / `MAP_UPDATE_RESUMED`，并保留该轮 `lidar_camera_alignment.json`。出现一次短暂恢复不等于地图更新性能问题已经彻底解决；若持续出现，需要根据新增计时进一步定位。

距起飞地面约 1.2 米只是局部定位高度差：它不能单独区分停在较高表面、仿真机体冻结或定位原点变化，需要结合 UE 场景和遥测判断。本次没有放宽高度容差来把这种状态强行判成成功落地。

## 2026-10-14：返航核验与回环关闭

`run_20261014_124829_081219` 在返航悬停后记录水平误差 0.408 m，被普通航点 0.4 m 判据拒绝，未进入正常任务的降落调用。探索任务现在用已有 `exploration_config.home_tolerance`（默认 0.6 m）完成落地前核验；返航航段仍收敛到 0.4 m 内。恢复起飞前航向后再次按同一原点容差核验。普通非探索任务继续使用其原有容差。

同次后台回环状态记录重建 233.344 秒，超过关闭等待的 60 秒。新增协作取消：关键帧构建、优化迭代、射线重建、历史雷达补算及逐行语义回放检查停止请求；取消按正常线程退出处理，未完成的版本不会发布。磁盘写入或单次底层运算仍需返回后才能取消，不将存活线程伪报成已关闭。

这两个异常不足以单独证明“桨叶停止但 UE 模型悬空”的物理原因；未修改实际落地确认、自动解锁、强制停桨或仿真位置。下一次实验需核对 sendMavLand、AUTO.LAND 接管及最终落地证据。

### 降落交接提前执行

`land()` 现在发送原 SDK `sendMavLand` 后立即等待新鲜 AUTO.LAND 心跳（最多 5 秒），确认后仅停止旧 Offboard 发送线程，不额外发送模式切换或停桨指令。没有接管确认则报错并保留旧发送线程，允许上层显式重试；不会伪报降落成功。无 MAVLink 心跳接口的 SDK 模式保留原指令流程。

正常任务先完成上述交接，再保存 landing 阶段检查点。异常清理发现降落已经发起时，不再悬停或重复发送 LAND，避免地图重建关闭等待期间旧悬停指令继续发送。真正落地仍要求高度、速度、新鲜遥测和稳定时间；不自动重新解锁已经停桨的悬空模型。
